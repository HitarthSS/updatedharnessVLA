# Adaptive Flash for RPent

This fork changes RPent's LIBERO Flash replay to avoid unused anchor localization and refresh a failed grasp's approach from the latest observation. It uses the original frozen models, released plans and primitive interfaces.

Based on [RLinf/RPent](https://github.com/RLinf/RPent) commit `945682a55c4e17d6bb686a80b162ff801e768157`. Upstream Apache-2.0 licensing and authorship are preserved. The changes are in `robots/libero/flash/replay.py`; regression tests are in `tests/unit_tests/robots/libero/test_adaptive_replay.py`.

## How it works

**Prune unused anchors.** Before the opening survey, identify anchors attached to valid `move_to` or `move_pose` commands within RPent's existing attachment-distance threshold. Skip anchors the program never uses. The frozen released corpus examined during development had 206 anchors; 42 were unused across 27 of 78 plans. This is 20.4% fewer surveyed anchors, not a measured 20.4% end-to-end speedup.

**Refresh failed approaches.** After `pi0_pick` reports failure, use the latest saved observation to locate the most recent approach anchor again. Preserve the original locator: SAM3 for segmentation anchors and Molmo for point anchors. Translate only approach movements attached to that anchor, retaining height, orientation and other arguments. Reject nonfinite readings, shifts greater than 8 cm and targets outside the existing reachable workspace; retain the previous approach when a reading is rejected or unavailable. Keep the existing maximum of three pick attempts. Successful first attempts incur no recovery perception query.

Inputs are the plan and relative anchor offsets, current RGB-D observations and calibration, robot state, grasp feedback and native episode terminal flags. The controller does not use simulator object poses, benchmark outcomes from other evaluation episodes, new training or new proprietary-model inference.

## Run

Follow upstream's [LIBERO setup](docs/source-en/rst_source/simulators/libero.rst) for simulator assets, Pi0.5 and SAM3. Install Molmo in a separate environment because its Transformers requirements differ from OpenPI:

```bash
uv venv --python 3.11 .venv-molmo
uv pip install --python .venv-molmo/bin/python -e '.[molmo]' \
  'torch==2.7.1' 'torchvision==0.22.1' 'transformers>=4.57,<5' einops
```

Set `MOLMO_CHECKPOINT_PATH` to the downloaded checkpoint, then start its local service in a separate terminal, from this repository:

```bash
CUDA_VISIBLE_DEVICES=0 PYTHONPATH="$PWD" \
  .venv-molmo/bin/python -m rpent.robots.components.molmo_server \
  --transport http --host 127.0.0.1 --port 23703
```

With the main LIBERO environment activated, set `PI05_CHECKPOINT_PATH` and `SAM3_CHECKPOINT_PATH`, then run one Spatial episode with an explicit reference horizon:

```bash
CUDA_VISIBLE_DEVICES=1 rpent --robot libero --libero-type pro \
  --planner flash --suite libero_spatial_task --task 0 --seed 1 \
  --memory-version GPT_5.5_xhigh \
  --memory-repo RLinf/RPent-memory@47f301ef33bf8d0e8c770342f16b3c39c6a0e8c1 \
  --molmo-endpoint http://127.0.0.1:23703 \
  --max-episode-steps 220 --output-dir logs/adaptive-spatial-t0-s1
```

Choose GPU indices that exist on your machine and have enough free memory; the example separates the grounder from the robot services. Pi0.5 and SAM3 are started by RPent unless external endpoints are supplied. For persistent services, use upstream's [advanced deployment guide](docs/source-en/rst_source/guides/advanced_deployment.rst).

## Horizon and evaluation limitations

RPent's released default is 10,000 native simulator actions. LIBERO-PRO's [reference evaluation example](https://github.com/RLinf/LIBERO-PRO) uses 220 for Spatial, 280 for Object, 300 for Goal and 520 for Long. Set `--max-episode-steps` explicitly for each suite. These are simulator actions, not wall-clock seconds. A 1.5x allowance is a separate experimental budget, not an established LIBERO-PRO rule.

Our initial experiments inherited the 10,000-step default. They are extended-budget experiments, not strict-horizon benchmark reproductions. Retrospective counting of recorded native-action frames showed that many successes exceeded the reference horizon. No claim of outperforming the published benchmark is made here. Shared GPU contention also prevents a clean latency comparison. Pruning changes preliminary robot motion; fresh perception may misidentify an anchor; recovery queries add latency.

The pinned installed LIBERO-PRO revision contained empty initial-state files for Spatial Task 3, Spatial Task 7 and Long Task 2. The released Flash corpus also lacked two complete task plans. Track unavailable cases explicitly, distinguish them from executed failures, and keep the expected case coverage visible. Do not substitute another task or manufacture a success. Our runs used seeds 0–9; the paper describes held-out seeds 1–10, another protocol difference requiring resolution before a paper-reproduction claim.

Success must come from the native environment termination predicate, not `pi0_pick` success or planner prose. Some RPent transcripts omit `environment_success` for LIBERO: the toolkit's success semantics accumulate `steps[].terminated` in `states.json`. A post-terminal extra-action error must remain visible even when earlier native termination established success. This fork preserves the frozen replay behavior, including that upstream edge case; it does not silently remove an executed failed attempt from scoring.

The publication includes source and offline tests. Credentials, checkpoints, machine-specific queue scripts, evaluation videos and partial score claims are excluded.

## Validation

From the repository root, using an environment with the test dependencies installed:

```bash
python -m pytest tests/unit_tests/robots/libero \
  tests/unit_tests/rpent/planner/test_api_contracts.py -q
```

The focused development check passed 174 tests, covering fresh-coordinate retries, unused-anchor pruning, successful-first-pick overhead, rejection of invalid or implausible readings, unchanged attempt limits, locator choice, orientation preservation and unavailable-mask fallback. These checks establish software behavior, not benchmark performance.
